## 2. Existing system architecture

The application should retain the following responsibilities:

- Hybrid RAG: retrieves relevant restaurant reviews and operational evidence.
- Classification Agent: complaint categories, aspects, sentiment, and severity.
- Trend Analysis Agent: historical complaint trends, supported forecasts, and satisfaction predictions.
- Root Cause Agent: evidence-backed hypotheses explaining operational problems.
- Action Planner Agent: ranked corrective actions, suggested owners, and KPIs.
- LangGraph: determines which agents are needed, coordinates parallel execution, manages dependencies, and handles failures.
- CrewAI: drafts and consolidates multi-agent findings into a coherent manager-friendly report and performs a separate draft-validation step.
- Quality Gate: checks evidence grounding, source traceability, data consistency, freshness, confidence, and unsupported claims.
- FastAPI: exposes backend capabilities to the frontend.
- React: provides the user interface and operational dashboards.
- Feedback and evaluation: records manager feedback and supports later DeepEval evaluation.

Use the actual implementation and data structures discovered in the repository. Do not assume a database table, model, endpoint, port, or field exists until verified.

# PART 2 — COMPLETE THE CREWAI DRAFTING AND CONSOLIDATION LAYER

This is a mandatory verification and implementation task.

First determine whether CrewAI drafting and validation already exist. If they exist, integrate and test them. If they are missing or incomplete, implement them without duplicating the existing LangGraph orchestration or Quality Gate.

## 2.1 Define the correct responsibility boundaries

LangGraph remains the primary workflow orchestrator.

The specialist agents remain independent services and retain their existing responsibilities.

CrewAI is responsible for synthesizing completed specialist findings into one clear operational report and reviewing that draft against the available evidence.

The Quality Gate remains the authoritative final validation stage.

Do not move the entire graph into CrewAI. Do not replace LangGraph with CrewAI. Do not run every agent twice merely to produce a report.

## 2.2 Implement a CrewAI drafting workflow

Use CrewAI's supported APIs and the existing LLM provider configuration.

Implement two narrowly scoped responsibilities:

### A. Operations Report Drafter

Inputs:

- Original manager question.
- Business scope and requested date range.
- Outputs from only the agents that actually ran.
- Retrieved evidence and source identifiers.
- Trend calculations and forecast metadata, if available.
- Root-cause hypotheses and their supporting evidence.
- Ranked action recommendations and proposed KPIs.
- Agent execution statuses and relevant warnings.

Responsibilities:

- Produce a concise executive summary.
- Explain the main operational findings.
- Identify the most important complaint categories and aspects.
- Summarize worsening or improving trends only when supported by data.
- Explain likely root causes while distinguishing hypotheses from established facts.
- Present prioritized recommendations with rationale, proposed owners, and measurable KPIs.
- Reference supporting evidence for material claims.
- Report data limitations and historical cutoff dates.
- Distinguish observed measurements from proposed targets and forecasts.
- Avoid repeating identical information from multiple agents.

The drafter must not invent review excerpts, numerical statistics, business IDs, trend values, or citations.

### B. Operations Report Validator

Validate the draft against the actual agent outputs, evidence, and Quality Gate inputs.

Check:

- Every material factual claim has traceable supporting evidence or a valid structured analytical result.
- Numerical claims match the supplied data and calculations.
- Recommendations are connected to identified operational issues.
- Root-cause hypotheses are described with appropriate uncertainty.
- Forecasts are not described as observed facts.
- The report uses the correct business and date scope.
- Conflicting agent results are surfaced rather than silently reconciled.
- Unsupported claims, fabricated sources, and unsupported confidence statements are removed or flagged.
- Stale data is disclosed.
- No private information has been reintroduced into the draft.

Return a structured validation result with findings, severity, claim references, and whether the draft can proceed.

The validator is a drafting-stage check. The existing Quality Gate must still execute afterward.

## 2.3 Conditional agent execution

The system must support both common multi-agent analysis and individual-agent invocation.

For a common question, LangGraph should select the relevant agents using explicit routing rules.

Examples:

- "Classify these complaints" → Classification Agent.
- "Which complaint categories are increasing?" → Trend Analysis Agent, with classification or retrieval support only when needed.
- "Why are customers complaining about long waits?" → retrieval and relevant classification/trend context, followed by Root Cause.
- "What should the restaurant fix first?" → the necessary diagnostic agents, Root Cause when required, and Action Planner.
- "Analyze the emerging problems, explain their causes, and recommend fixes" → Classification and Trend in parallel when both are required, then Root Cause, then Action Planner.

Do not force all four agents to execute for every query.

If multiple agents are required, consolidate their outputs through the CrewAI drafting workflow.

For an individual-agent request, allow the selected agent to run independently and return its structured result. Do not force a full multi-agent report unless explicitly requested.

The frontend must identify which agents ran, which were skipped, and why.

## 2.4 CrewAI integration requirements

- Use the existing provider and configuration; never hardcode credentials.
- Use Pydantic or existing schemas for structured outputs.
- Pass compact, relevant, masked context rather than entire raw datasets.
- Preserve source identifiers through drafting and validation.
- Keep the drafter and validator separate from the four specialist agents.
- Handle timeout, malformed output, and LLM failure.
- Do not report successful validation when validation failed or was skipped.
- Do not let a CrewAI failure erase the original specialist outputs.
- Preserve the Quality Gate as the final validation authority.
- Add unit and integration tests.
- Document the actual flow and report whether CrewAI ran successfully.

If CrewAI is already implemented, fix or integrate the existing implementation rather than creating another crew with duplicate responsibilities.

# PART 3 — FASTAPI BACKEND AND INTEGRATION

Implement a thin FastAPI gateway. The API is the connection between React and the existing AI system, not another orchestration engine.

Do not make the browser communicate directly with internal A2A agent services. Keep agent selection and orchestration in the backend.

Use existing API conventions if already present. Otherwise, implement the following endpoint design.

## 3.1 Common analysis

### POST `/api/v1/analysis`

Accept:

- `query`: required question.
- `mode`: `auto` or `agent`.
- `agent`: required when `mode=agent`; one of the supported agent identifiers.
- `business_id`: optional only if the current backend supports general scope.
- `start_date` and `end_date`: optional supported date filters.
- `filters`: optional metadata filters supported by the retrieval system.

For `mode=auto`, route through the existing LangGraph workflow.

For `mode=agent`, call the selected agent through the existing A2A interface.

Return a validated, frontend-friendly response containing, where available:

- Request ID.
- Query and actual business/date scope.
- Execution mode and selected agent.
- Overall execution status.
- Final consolidated report for multi-agent analysis.
- Structured individual-agent output for individual-agent mode.
- Complaint categories, aspects, sentiment, and severity.
- Trend findings, actual data range, and forecast metadata.
- Root-cause hypotheses and supporting evidence.
- Ranked actions, proposed owners, and KPIs.
- Evidence excerpts and source identifiers.
- Quality Gate status, confidence information, and groundedness findings.
- CrewAI drafting and validation status.
- Agent execution trace and per-stage timings.
- Warnings, partial failures, and data freshness information.

Use explicit response schemas. Do not expose arbitrary internal graph state.

### GET `/api/v1/agents/status`

Report the actual status of each agent service.

Use real health checks, A2A connectivity checks, or existing telemetry. If the service is unreachable or its status cannot be verified, report `unknown` or `unavailable` as appropriate.

Do not report an agent as available simply because it is listed in configuration.

### GET `/api/v1/health`

Provide backend liveness and readiness information.

Readiness should reflect required dependencies and service availability without leaking secrets or infrastructure details.

### GET `/api/v1/analysis/{request_id}`

Implement this if the project has, or can reasonably support, persisted analysis history. Return an existing result or a clear not-found response.

Do not pretend in-memory state is durable persistence.

### GET `/api/v1/scenarios`

Return supported manager demonstration scenarios from a configuration or existing scenario registry.

Each scenario should have a title, description, sample query, execution mode, and supported business/date filters.

Use scenarios grounded in the actual restaurant dataset. Do not invent restaurant IDs or imply that unavailable data exists.

### POST `/api/v1/feedback`

Accept feedback against a completed request, including:

- `request_id`.
- A useful/not-useful rating.
- Optional error categories.
- Optional manager comments.

Validate the request and persist feedback using the existing database if possible. If persistence is missing, implement a small, durable feedback store using the project's established database approach.

Do not store unnecessary personal data or unmasked review content in feedback records.

### GET `/api/v1/feedback/summary`

Return aggregated feedback statistics when supported by the stored data.

### GET `/api/v1/evaluation/summary`

Return the latest actual evaluation results when available. Clearly distinguish results that have run from evaluations that are pending or unavailable.

Do not fabricate DeepEval metrics.

## 3.2 Execution trace contract

Represent execution as structured events, not a single string.

Each event should contain fields such as:

- `event_id`.
- `request_id`.
- `stage`.
- `component`.
- `status`.
- `started_at` and `finished_at`, when available.
- `duration_ms`, when measurable.
- `input_summary`, safely redacted.
- `output_summary`, safely redacted.
- `source_ids`, where applicable.
- `warnings` or `error_summary`.

Track meaningful events such as:

1. Request validation and guardrails.
2. Query planning and metadata filters.
3. Hybrid retrieval and evidence selection.
4. PII Gate 2.
5. Classification and Trend branches, including actual overlap in execution.
6. Root Cause.
7. Action Planner.
8. CrewAI drafting.
9. CrewAI draft validation.
10. Quality Gate.
11. Final response preparation.

Record skipped stages as skipped, not successful.

Use actual timestamps and timings. Do not fabricate parallel execution or claim that an agent executed when it did not.

If streaming progress is feasible within the existing architecture, expose Server-Sent Events through a dedicated endpoint. Otherwise, return the completed trace with truthful timings. Do not add WebSockets simply for decoration.
