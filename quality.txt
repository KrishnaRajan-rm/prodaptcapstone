Your task is to implement **Phase 4: Quality, Privacy, Evidence Grounding, and Confidence Validation**.

The objective is to ensure that the orchestrated system produces trustworthy, evidence-supported, privacy-safe operational recommendations.

**Do not rebuild existing components. Inspect the repository first, reuse existing implementations, and integrate this phase into the existing LangGraph workflow.**

## 3. Integrate PII Gate 2

Implement a second privacy checkpoint before review content and queries are sent to LLMs.

### Requirements

- Inspect and reuse the existing PII detection and masking logic.
- Scan the relevant query and retrieved evidence for residual personal information.
- Replace detected personal information with reversible request-scoped tokens, following the existing PII Gate 1 conventions.
- Keep the token mapping in a protected, request-scoped vault or equivalent secure mechanism.
- Do not send raw PII to external LLM calls.
- If masking fails or sensitive data remains, block the affected model call and return a structured error or safe fallback.
- Preserve the evidence references needed to trace findings to source records.
- Prevent tokens from being confused across different requests.
- Ensure errors, exceptions, debug output, and traces do not expose unmasked personal information.

The existing agents may perform their own retrieval. Inspect these paths and make sure the privacy boundary covers every applicable LLM call, not just the initial orchestration request.

Do not rebuild Hybrid RAG or the four agents to accomplish this. Prefer integrating the existing masking component at the appropriate shared boundary.

## 4. Implement the Quality Gate

Add a Quality Gate node after the Action Planner and before the final response is returned.

It must validate the combined outputs from Classification, Trend Analysis, Root Cause Analysis, and Action Planning.

### A. Evidence-grounding validation

For every material finding, hypothesis, forecast, and recommendation:

1. Check whether the supporting source IDs actually exist in the available evidence context.
2. Verify that quoted review excerpts match the original source text, allowing only documented normalization.
3. Check that claims about a particular business are supported by evidence belonging to that business.
4. Verify that claims fall within the relevant date range.
5. Distinguish individual review evidence from aggregate statistics.
6. Identify unsupported claims, missing citations, and contradictions between agents.
7. Ensure a cited review genuinely supports the associated claim rather than merely mentioning a related topic.

A valid source ID alone does not prove that a claim is supported.

For example, if the user asks about emerging problems but a root-cause hypothesis discusses new-location onboarding without evidence that the selected business is newly opened, flag the unsupported inference.

Do not fabricate replacement evidence or silently turn unsupported hypotheses into facts.

### B. Statistical and trend validation

Where sufficient source data is available, verify:

- Complaint counts and percentages against their underlying data.
- Percentage changes and comparison periods.
- Historical date ranges and data freshness.
- Whether a claimed worsening trend is actually supported.
- Whether complaint counts are being confused with complaint rates.
- Whether forecasts are labeled as predictions rather than observed facts.
- Whether reported evaluation metrics correspond to actual evaluation results.
- Whether satisfaction predictions are supported by the available labels and model evaluation.

For example, if the dataset ends in January 2022, do not present a forecast beginning in February 2022 as a current forecast in October 2026. Clearly report the historical cutoff and explain that the data is stale for a current operational forecast.

Use deterministic calculations and existing data sources for numerical verification wherever possible.

### C. Recommendation validation

Validate Action Planner outputs against the preceding findings.

- Every recommended action must map to an identified operational problem or supported finding.
- Priorities must be consistent with the available severity, frequency, trends, and impact information.
- Owners must be reasonable operational roles, not invented named employees.
- KPIs must measure the intended outcome.
- Proposed targets must be labeled as proposed unless supported by an established business policy or baseline.
- Operational standards, financial claims, and regulatory requirements must not be presented as verified facts without appropriate supporting evidence.
- Flag recommendations that rely on unsupported assumptions.

Do not automatically reject a reasonable hypothesis merely because it is not proven. Instead, distinguish evidence-supported findings, plausible hypotheses, and unverified assumptions.

### D. Contradiction detection

Compare agent outputs for inconsistencies.

Examples:
- Classification identifies only mild complaints, but the Action Planner ranks the issue as critical without supporting evidence.
- The Trend Agent reports improving food quality, while the final report claims food quality is deteriorating.
- A source review belongs to a different business from the requested business.
- A root-cause hypothesis conflicts with the supplied evidence.

Record contradictions and either resolve them using verified source data or flag them for review.

## 5. Confidence scoring

Implement an explainable confidence score for important claims and recommendations.

Use a deterministic scoring approach based on factors such as:

- Evidence relevance and directness.
- Source traceability.
- Agreement between independent findings, where applicable.
- Data completeness and freshness.
- Consistency with numerical results.
- Contradictory evidence and unsupported assumptions.

Document the scoring formula, component weights, and thresholds.

Requirements:

- Do not treat an LLM's self-reported confidence as calibrated probability.
- Do not assign high confidence simply because multiple agents repeat the same unsupported claim.
- Avoid double-counting evidence shared by agents.
- Flag claims below the configured confidence threshold.
- Preserve the difference between evidence confidence and forecast-model performance.
- Use `unknown` or an equivalent status when confidence cannot be assessed.

The score should be explainable to a developer or reviewer. Do not claim that it is statistically calibrated unless calibration has actually been measured.

## 6. LLM-as-judge

Implement an LLM-as-judge check for the final operational analysis, reusing the configured LLM provider.

The judge should evaluate:

- Faithfulness to supplied evidence.
- Citation correctness.
- Unsupported claims.
- Contradictions.
- Relevance to the original business query.
- Whether recommendations follow from the findings.
- Whether limitations and uncertainty are communicated clearly.

Provide the judge with a compact, masked representation of the claims and their supporting evidence. Do not send the entire review corpus unnecessarily.

The judge must return a structured, validated result containing the verdict, identified issues, supporting references, and suggested remediation.

Important rules:

- Treat judge output as an additional validation signal, not ground truth.
- Do not allow the judge to invent evidence.
- Do not use the judge's approval as a substitute for deterministic source and arithmetic checks.
- If the judge fails or times out, mark that validation as unavailable and apply the configured safe policy.
- Avoid unbounded retry loops or repeated judge calls.
- Record judge latency separately.

## 7. Quality Gate decision and routing

Implement clear outcomes:

- `passed`: required checks passed and no blocking issue remains.
- `flagged`: material claims or recommendations need review.
- `blocked`: critical privacy, provenance, or correctness failure prevents safe release.

Use the project's existing status conventions if they already provide equivalent states.

Examples of blocking conditions include:
- A failed PII safety check before an LLM call.
- Evidence references that cannot be verified for a critical claim.
- A business-ID mismatch that could expose or attribute another business's information.
- Material fabricated evidence or a severe unsupported safety claim.

Minor uncertainty should not automatically block an entire report. It can be flagged and clearly disclosed.

The graph must not return a `passed` status merely because the Quality Gate node executed successfully.

## 8. Final-response PII decoding

Implement or integrate role-based PII decoding at the final response boundary, after quality validation.

Requirements:

- Restore reversible tokens only when the caller's authenticated role and permissions authorize access.
- Analysts or restricted roles must receive masked content.
- Manager access must follow the existing authorization policy; do not assume every caller is a manager.
- Decode only tokens belonging to the current request.
- Never decode PII in internal logs, telemetry, exception messages, agent traces, or the Quality Gate's LLM payload.
- Ensure unauthorized callers cannot supply arbitrary tokens to recover personal information.
- If authentication or authorization infrastructure is not implemented, fail closed for unmasking and document the missing dependency.
- Preserve the existing response schema wherever possible.

Do not expose or return the token vault itself.
